# Coze SaaS 边界 + 自建扩展 · 架构清晰说明

> 答疑文档。读者：你 + 工程师 1（架构师）+ 高层。
> 解决疑问："Coze 是 SaaS，那这些自建方案到底跑在哪？怎么跟 Coze 连？"

## 0. 核心问题

你说得**完全对**：Coze 企业版是 SaaS——bot / 工作流 / KB / 长期记忆 全部跑在**字节/火山的服务器**上。
但 **SaaS ≠ 封闭系统**。Coze 提供了 **5 个明确的扩展接入点**，让你公司在自家服务器上跑的服务能跟 Coze 双向通信。

我之前提的所有自建方案——AI Gateway、Feishu Bridge、CRM 插件——**都是跑在你公司服务器上**，通过这些扩展点连 Coze。

不矛盾。这是**企业级 SaaS 的标准模式**（类似你怎么扩展飞书、Salesforce、Notion）。

## 1. SaaS 的真正边界（什么是 Coze 的 / 什么是你的）

| **数据库（扣子 DB）** | 表格化数据 |

| **Coze Loop** | 评测/观测/Trace 平台 |

| **多模型供应** | 豆包/DeepSeek/Kimi 的对接 |
| **企业账号体系** | 成员、空间、角色 |

→ **你买的就是这一套**。每月 ¥5,980+。

| 模块 | 解释 |
|---|---|

→ **跑在火山 ECS / 阿里云 / 腾讯云 / 你机房 都行**。

## 2. Coze SaaS 的 5 个扩展接入点

### 2.1 ① 自定义插件（OpenAPI 3.0）

**Coze 调出你的服务**：bot 在工作流里通过插件节点调你的 HTTPS API。

```
Coze SaaS ──HTTPS Bearer──→ https://crm-api.your-company.com/customers/123
                            （你的 CRM 插件服务，跑在你 ECS）
```

**用途**：
- 接公司内部系统（CRM / HR / 工单 / SQL / BI）
- 数据查询（注意 §3 的 `DATA-SECURITY.md` 八原则）

**实现**：你工程师 2 写一个 FastAPI/Spring Boot 服务，暴露 OpenAPI，Coze 后台导入。

### 2.2 ② 自定义模型（OpenAI 兼容）

**Coze 调出你的模型 endpoint**：bot 选模型时选你接入的"自定义模型"。

```
Coze SaaS ──/v1/chat/completions──→ https://ai-gw.your-company.com
                                    （你的 AI Gateway，跑在你 ECS）
                                    │
                                    ├→ OpenAI / Claude
                                    ├→ 自部署 Qwen / Llama
                                    └→ DeepSeek / Doubao
```

**用途**：
- 接 OpenAI / Claude / Gemini 等第三方
- 接公司自部署的开源模型
- 统一审计 + 限流 + 成本核算
- PII 拦截

**实现**：LiteLLM Proxy + 你写的 PII Blocker callback，Coze 后台导入"自定义模型"。

### 2.3 ③ Coze OpenAPI（你调进 Coze）

**你的服务调进 Coze**：通过 PAT 鉴权，调 Coze 提供的 REST API。

```
你的服务（Bridge / 同步器）──Bearer PAT──→ api.coze.cn
   - POST /v1/datasets/.../documents       上传文档到 KB
   - POST /v3/chat                          触发 bot
   - POST /v1/enterprises/.../members       添加成员
   - POST /v1/workflow/run                  调用工作流
```

**用途**：
- 飞书数据同步进 KB（Bridge 用）
- 通讯录同步成员
- 触发 bot 处理外部事件
- 批量管理 bot

**实现**：在你 ECS 上跑一个服务，封装 `CozeClient`（参考 `FEISHU-SYNC-BRIDGE.md §3.5`）。

### 2.4 ④ 回调/触发器（Coze 主动调你）

**Coze 主动调出**：工作流执行后通过 webhook 通知你。

```
Coze 工作流执行完
  │
  └→ 调你公司的 webhook URL
      （记日志 / 触发后续业务流 / 同步到自有系统）
```

**用途**：
- 工作流结果回流自有系统
- 异步任务完成通知
- 审计日志归档

**实现**：在 Coze 工作流里加 HTTP 节点 → 调你的 webhook。

### 2.5 ⑤ 第三方集成（飞书/微信/抖音）

**Coze 跟第三方打通**：飞书集成、抖音渠道、微信公众号等。

```
Coze ⇄ 飞书 OpenAPI
  - 读消息、文档、多维表格、日历、任务、通讯录
  - 发布 bot 到飞书企业应用
  - 自定义机器人 webhook
```

**用途**：你 800 人公司用飞书，这是核心入口。
**实现**：Coze 后台一键开启，按指引授权。

## 3. 我提出过的自建方案对应表

| 自建方案 | 跑在哪 | 通过哪个接入点 | 是否必须 |
|---|---|---|---|
| **AI Gateway**（LiteLLM Proxy）| 你 ECS | ② 自定义模型 | 仅当用第三方模型 |
| **Feishu→Coze Bridge** | 你 ECS | ③ Coze OpenAPI | 仅当要"全量飞书数据实时入 Coze" |

| **HR 插件** | 你 ECS | ① 自定义插件 | 看是否做 HR bot |
| **数据安全过滤层** | 你 ECS（在 AI Gateway 里）| ② 间接走 | 保健品行业**强烈建议** |
| **监控仪表盘** | 你 ECS | ③ 读 Coze API（trace）| 推广期推荐 |
| **多 bot 路由器** | 不用自建 | 直接用 Coze 多 Agent 模式 | - |
| **反思工作流（方案 A）** | 不用自建 | 直接用 Coze 工作流 + LLM | - |
| **memory-integration**（最早设计）| ❌ 不要建 | - | Coze 已替代 |
| **coze-control**（GitOps）| 不用自建 | Coze Loop 已替代 | - |

**关键洞察**：80% 的"自建"其实是给 Coze SaaS **配的扩展插件**，而不是替代 Coze。

## 6. 为什么 800 人企业**必须扩展**（不能纯 SaaS）

### 6.1 5 个不可绕过的扩展需求

| 需求 | 为什么纯 SaaS 不行 |
|---|---|
| **接 CRM/HR/SQL** | Coze 不可能内置你公司的内部系统，必须自建插件 |
| **飞书全量数据实时入 Coze** | Coze 飞书集成是"按需读"，不主动 listen 事件 |
| **接 GPT/Claude（用于通用任务）** | Coze 自定义模型需要外部 OpenAI 兼容 endpoint |
| **PII 拦截（保健品合规）** | Coze 内置内容安全是关键词级，不做企业级 PII 检测 |
| **监控/审计（合规要求）** | Coze Loop 是 SaaS，部分日志要回流自有系统才能符合等保 |

### 6.2 不扩展会怎样

- 销售 bot 不能查你公司 CRM → bot 只能聊天不能干活
- 客户在飞书发消息 bot 看不到 → 飞书 + Coze 各自孤岛
- 想用 Claude 做合同审查 → 没法接
- PII 进了海外模型 → 监管罚款风险
- 800 人用得越多越乱 → 治理失控

## 7. 一个**完全不自建**的极简起步方案

如果你想**先验证再投入自建**，可以这样：

### 7.1 第一周（极简 PoC）

```
完全用 Coze SaaS：
□ 买企业旗舰版 + 20 席位
□ 开飞书集成（一键）
□ 装内置插件（搜索、计算器等）
□ 用扣子官方模型（豆包/DeepSeek）
□ 在 UI 里手搭一个简单销售助手 bot
□ 知识库手动上传 SOP 和产品手册
□ 客户档案手动维护在飞书多维表格
□ 让 5 个销售试用一周

什么都不自建。
```

**能验证什么**：
- ✅ Coze 基本能力（工作流、KB 检索、飞书入口）
- ✅ 销售用 bot 的接受度
- ✅ 推广可行性

**不能验证什么**：
- ❌ 接公司 CRM 后的体验（无插件）
- ❌ GPT/Claude 在某些场景的优势
- ❌ 飞书全量数据进 Coze 的价值
- ❌ 800 人推广时的合规
- ❌ 离职员工数据自动清理

### 7.2 第二周开始按需扩展

| 痛点出现 | 才上对应自建 |
|---|---|
| 销售反馈"档案查不到/查不全" | → 自建 CRM 插件 |
| 业务方说"GPT 写营销文案更好" | → 自建 AI Gateway |
| 飞书会议纪要漏了关键客户信息 | → 自建 Feishu Bridge |
| 法务说"PII 拦截不够" | → 自建数据安全层 |
| 推广爆账单 | → 自建监控仪表盘 |

**这是更稳健的路径**——不要一开始就把 7 工程师全扔进自建里，先 1-2 个人用 SaaS 跑 PoC。

## 8. 自建跟 Coze 升级的兼容性

### 8.1 Coze 自己升级会破坏自建吗

| Coze 升级 | 影响你的自建 |
|---|---|
| 改 UI / 改交互 | ❌ 不影响（你不通过 UI 调用）|
| 改插件协议 | ⚠️ 可能影响 CRM 插件（OpenAPI 标准变化罕见）|
| 改 OpenAPI 端点 | ⚠️ 可能影响 Bridge / 监控（关注 changelog）|
| 改自定义模型协议 | ⚠️ 可能影响 AI Gateway（罕见，OpenAI 协议很稳定）|
| 出新功能（如 Memory.md）| ✅ 可能让你某些自建变得多余（看 `MEMORY-COMPARISON.md`）|

**结论**：自建跟 SaaS **松耦合**，但**不是完全隔离**——要订阅 Coze 的 [changelog](https://docs.coze.cn/developer_guides/changelog)，每月 review 一次。

### 8.2 自建带来的"逃生通道"

如果哪天：
- Coze 涨价到不可接受
- 字节政策变化
- 你公司战略需要换平台

→ 由于你**所有插件、Gateway、Bridge 都是开源协议（OpenAPI / OpenAI 兼容）**，可以无缝迁移到：
- Coze Studio 自部署
- Dify / FastGPT
- 自研

**Coze 的 Eino 编排引擎也是开源**——工作流配置可 export 出来跑。

## 11. FAQ

### Q1：Coze 是 SaaS，那我企业旗舰版的钱花在哪？
> 你买的是：bot 编排引擎、工作流执行算力、KB 向量索引、模型调用通道、企业账号体系。这些都是大头，自建成本远高于 ¥5,980/月（自建 RAG 一个工程师月薪就够你跟 Coze 玩 3 年）。

### Q2：那我能完全自部署吗？
> 可以，**Coze Studio 是 Apache 2.0 开源**（GitHub: coze-dev/coze-studio）。但：
> - 没有 Agent World（云电脑/云手机/邮箱）
> - SSO/VPC 等企业特性要重做
> - 模型对接要自己配
> - 运维 ≥ 1 名工程师全职
> - 适合 1000+ 大企业 + 数据极敏感 + 有专门 AI 团队

### Q3：自建会不会被字节看到我数据？
> 你自建的部分**只在你公司服务器**，字节看不到。
> Coze SaaS 部分按它的数据保护协议（已承诺不训练）。
> 关键 PII 通过 §5 的接入点设计**不进入** Coze SaaS，只在你自建侧流转。

### Q4：800 人公司一定要自建吗？
> 不是"一定"，而是"建议"。
> - 50 人以下：纯 SaaS 够
> - 50-300 人：CRM 插件 + 飞书集成
> - 300-1000 人：再加 AI Gateway + 数据安全层
> - 1000+ 人：考虑部分自部署

### Q5：自建和 SaaS 比性价比怎么样？
> 你公司 800 人 + 7 工程师：
> - SaaS：¥61,180/月（账面）
> - 自建扩展：¥3,000/月 基础设施 + 摊销 1-2 工程师
> - 总：约 ¥7-10 万/月，每人 ¥80-120
> - 对比飞书企业版（每人 ¥99）+ 阿里云 SaaS（每人 ¥50）等
>
> **每人每月 ¥100 左右，业内主流水平**。

### Q6：如果只买 Coze 企业版，自建一概不做，能跑通吗？
> 能跑通"概念演示级"。但：
> - 销售 bot 看不到你公司 CRM → bot 只是聊天伙伴
> - 飞书消息全要在 Coze UI 里看 → 员工不愿意开第二个标签
> - 数据合规风险（PII 难控）
> - 800 人推广时 bot 错答率高（无评测+反思）
>
> **中型以上企业不建议纯 SaaS**。

---

## 12. 一句话总结

**Coze SaaS 是 80%，你公司自建扩展是 20%——但这 20% 决定了你 800 人能不能真的用起来**。

不自建 = bot 只是个聊天玩具。
全自建 = 浪费 SaaS 红利，重复造轮子。
**SaaS + 5 个扩展点 = 80/20 最优解**。
